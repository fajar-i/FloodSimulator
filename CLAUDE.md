## Project

**Dewan Bengawan** — an educational flood-simulation / city-builder game built in **Unity 6 (6000.4.1f1)** with the **Universal Render Pipeline (17.4)** and the new **Input System (1.19)**. The player zones a city on a voxel terrain, then runs a cellular-automata flood simulation to stress-test the urban plan. Most code comments and `Debug.Log` strings are in **Indonesian** — match that convention when editing existing files.

Design intent and MVP status live in `docs/` (`project_status_report.md`, `dewan_bengawan_mvp_handoff.md`, `roadmap_baru.md`). Read these before adding features — they define the MoSCoW scope and which modules are still unbuilt (Policy Cards, HUD, Heatmap overlay, Harvest screen).

## Building, Running, Testing

There is no CLI build/test workflow — this is a Unity Editor project.

- **Open / run:** open the project in Unity Editor 6000.4.1f1 and enter Play mode. `Assembly-CSharp.csproj`, `*.slnx`, and the `Library/` folder are auto-generated by Unity — never hand-edit them; regenerate by reopening in the Editor.
- **Tests:** Unity Test Framework (`com.unity.test-framework`) is installed. Run tests via **Window → General → Test Runner** in the Editor. No test assemblies exist yet.
- **Runtime controls (no UI yet — all keyboard/mouse driven):**
  - `Enter` — advance `GameState` (Planning → Construction → Simulation → Harvest).
  - During **Planning**: mouse paints zones; digit keys `0`–`5` select the active voxel/zone ID (see `VoxelID`).
  - During **Simulation**: hold `Space` to inject water from the top of the world.

## Architecture

The simulation is a **voxel grid driven by a `GameManager` state machine**, with physics in Burst jobs and rendering split between procedural chunk meshes (terrain/water) and GPU-instanced props (buildings/roads).

### Core data: voxels
- `VoxelCell` (`Assets/GameManager/VoxelCell.cs`) — a struct per cell holding water `amount`, `isSolid`, `blockType` (the `VoxelID`), `rotation`, and hydrology fields (`zoneType`, `absorptionRate`, `flowFriction`, `isPollutionSource`).
- `VoxelID` (`Assets/GameManager/VoxelID.cs`) — the single source of truth for block IDs, banded by range: nature `0–9`, infrastructure `10–29`, zones `30–39`, completed buildings `40+`. `VoxelHelper.InitializeHydrology` maps a `blockType` to its hydrology constants — **always set hydrology through this helper** so absorption/friction stay consistent.
- `ZoneType` enum is centralized in `VoxelCell.cs` (handoff standard) — do not redefine it elsewhere.

### World & chunking
- `VoxelWorld` (`Assets/GameManager/VoxelWorld.cs`) owns the simulation state as **two persistent `NativeArray<VoxelCell>` buffers** (`ActiveGrid` / `NextGrid`) for double-buffered CA. Indexing convention everywhere: `idx = x + width*y + width*height*z`.
- The world (default `32³`) is split into `16³` `WaterChunk`s (`Assets/WaterSimulation/WaterChunk.cs`), each a GameObject with its own mesh, for incremental visual updates. `NativeArray`s are `Allocator.Persistent` — they must be disposed; be careful adding new ones.

### Water physics (Burst jobs)
- `WaterSimulationSystem` (`Assets/WaterSimulation/WaterSimulationSystem.cs`) schedules `WaterPullJob` (`WaterSimulationJob.cs`), a `[BurstCompile] IJobParallelFor` reading `ActiveGrid` and writing `NextGrid`, then swaps buffers.
- The CA uses 3D Von Neumann neighbors (4 lateral + 2 vertical for gravity), reads `flowFriction` per-cell for lateral spread speed, and clamps flow to avoid overshoot. `WaterMeshJob` (`WaterMeshJob.cs`) rebuilds chunk meshes with face-culling and UV-atlas coordinates.

### City generation & rendering
- `CityGameManager` (`Assets/CityRendererSystem/CityGameManager.cs`) orchestrates the Construction phase as a coroutine: `CityGenerator` lays the road network (hierarchical grid: arterial + local roads), `CityAutoBuilder` places buildings (cut-&-fill terrain leveling, WFC-style), then `CityRendererSystem` renders.
- `CityRendererSystem` (`Assets/CityRendererSystem/CityRendererSystem.cs`) scans the world and renders solid props via `Graphics.DrawMeshInstanced`, batched through `RenderBatch` (1023-instance chunks to respect the instancing cap, pre-allocated and reused to avoid GC churn). Connectable infrastructure (roads/sewers) picks a mesh + rotation via a 4-direction bitmask (Standalone/End/Straight/Corner/T/Cross).
- `BuildingRegistry` (`Assets/CityRendererSystem/BuildingRegistry.cs`) is a `ScriptableObject` mapping each `byte` ID to mesh/material and a `RenderType` (`StaticProp` vs `Connectable`). The `connectionMeshes` array order is fixed: `0:Standalone, 1:End, 2:Straight, 3:Corner, 4:T, 5:Cross`.

### Orchestration & subsystem convention
- `GameManager` (`Assets/GameManager/GameManager.cs`) wires the modules via serialized references and drives them per-state in `Update`. Subsystems do **not** self-update in their own `Update()`; instead they expose a `SystemUpdate(VoxelWorld)` / `OnUpdate()` method that `GameManager` calls in the correct phase and order (this avoids race conditions and enforces deterministic update order). Follow this pattern when adding a new system: take `VoxelWorld` as a parameter rather than caching globals, and let `GameManager` call you.

### Gotchas
- Solid voxels that are instanced props (roads, sewers, buildings) are deliberately culled from the base chunk mesh so they don't z-fight with their instanced models — keep that separation when adding block types.
- A solid voxel only renders as an instanced prop if it has a matching entry in `BuildingRegistry`.
